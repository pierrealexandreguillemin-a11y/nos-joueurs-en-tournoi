End-to-end reproduction (prod has no `NEXT_PUBLIC_SYNC_SECRET`, so the

```bash
node -e "const c=require('crypto');const s='checkup-probe',t=Date.now();const h=c.createHmac('sha256','default-dev-secret').update(s+':'+t).digest('hex');fetch('https://nos-joueurs-en-tournoi.vercel.app/api/events/fetch?clubSlug='+s,{headers:{'X-Sync-Token':h+':'+t}}).then(async r=>console.log(r.status,await r.text()))"
# expected today: 500 {"error":"Internal server error"}   (auth passes, Redis fails)
```

Side effects:
- `proxy.ts` rate limiting fails open on every API call (`[proxy] Rate limit check failed`), so
  `/api/scrape` currently has **no rate limit**, and each request waits several seconds on the
  failed DNS lookup before proceeding.
- Unit tests stay green because Redis is mocked — no test watches the real store.

Probable cause (primary source: Upstash mails to the owner, 2026-03-23 and 2026-05-07,
"Upstash Redis Database Inactivity First Notice"): free-tier Vercel Marketplace databases with no
traffic are archived — "Backing up your data / Removing the database instance (you can still
restore your data later if needed)". The mails name the database `hay-chess-tracker`; that this is
the instance behind `charming-troll-21280` is **not verified** (needs the Upstash/Vercel console).

Also observed: production env vars `KV_REST_API_URL` / `KV_REST_API_TOKEN` were set by hand on
2026-02-18 (`configurationId: null`) and the Upstash integration lists **no linked project** — a
re-provisioned store will not inject its variables automatically unless it is connected to the
project.

### C1 — verified afterwards in the Upstash console, and decision

- Upstash console (via Vercel SSO) lists the archived store as `hay-chess-tracker`, endpoint
  **`charming-troll`**, AWS EU-CENTRAL-1, status DELETED, with a Restore action. This app is the
  rebrand of hay-chess-tracker (commits of 2026-02-14), hence the name.
- The console states: "Free databases are deleted by automation after 14 days of inactivity"
  (the FAQ says "a minimum of 30 days" — the console is the stricter, more recent statement).
- Restore requires a **target database created beforehand**. The account's single free Upstash
  slot is held by `claudine-contact` (another, active project): the Vercel install dialog offers
  no Free plan, only Pay As You Go / Fixed.
- Owner's decision (2026-10-20): **Neon Postgres, free plan**, rather than a paid Upstash
  database. Consequences:
  - `src/lib/kv.ts` (Upstash) is replaced by a Postgres store; schema in `db/schema.sql`.
  - Rate limiting moves out of the app to the **Vercel WAF** (Hobby: 1 rate-limit rule per
    project, fixed window, keyed by IP, 1M requests included — vercel.com/docs/vercel-firewall/
    vercel-waf/rate-limiting). One rule on `/api/*`, 30 req / 60 s / IP. Trade-off: the former
    10 req/60 s limit on `/api/events/*` is relaxed to 30; in exchange the limit no longer depends
    on a database and cannot fail open (which is what happened during this outage).
  - Old Redis data is not migrated: Upstash restores only into an Upstash target. Each browser
    still holds its club's data in localStorage; it reaches the new store when someone presses
    "Envoyer vers le cloud" in the events manager (`cloudUpload` → `syncToUpstash`). Sync is
    manual, not automatic.
  - Neon free plan: compute suspends after 5 min idle (first request wakes it); "none of the
    limits delete your data" (neon.com/docs/introduction/plans). Deletion of inactive free
    projects is not documented either way.

## C2 — Pairings parser never matches real FFE round pages

`parsePairings` keeps `<td>` whose class contains `papi_liste_f|papi_liste_c`. On the live round
page those classes are on the `<tr>`; cells carry `papi_r|papi_c|papi_l`:

```html
<tr class=papi_liste_f>
  <td class=papi_r>1</td> <td class=papi_c>6</td> <td class=papi_l>BEN AMMAR LAURANS Nael</td> ...
```

```bash
curl -s -A "Mozilla/5.0" "https://www.echecs.asso.fr/Resultats.aspx?URL=Tournois/Id/68994/68994&Action=09" | grep -A3 "tr class=papi_liste_f" | head -4
```

Measured with the real parser on tournament 68994, round 9: **0 pairings** (32 boards on the page).
The unit-test fixture (`parser.test.ts`, `makePairingHTML`) puts the class on `<td>`, which is why
the suite passes. Whether the FFE markup changed since 2026-02-24 or the fixture never matched it
cannot be told from here: no real round page was ever saved as a fixture.

Impact: the pairings tab (`TournamentTabs.tsx` → `filterClubPairings`) shows nothing.

## C3 — Results parser: layout row matched as a player row

`parseResults` selects every `<tr>` that *contains* a `div.papi_joueur_box`. The page-layout row
wrapping the whole grid also contains them: 65 rows matched for 64 players. That row yields the
first player of the grid a second time, read from the wrong `<td>`, so its performance is lost —
and `parseFFePages` keeps the **first** (bad) copy when it deduplicates.

Measured on 68994: rows matched 65 vs boxes 64; selecting rows whose `td` directly holds the box
gives 64 rows and performance `2162` for player #1 (undefined today). Names, Elo, points, Tr.,
Buchholz and the 9 round results are parsed correctly.
